# 2.2.0 帧率、成像与稳定性

本版在已连接的 MaixCAM Pro / GC4653 上将普通视频的处理上限设为 **45 fps**；传感器请求 60 fps。完整图像仍为 640 × 480，JPEG 质量 75。原 YOLO11n 320 × 224 INT8 模型、置信度 0.5、IoU 0.45、缩放插值和双缓冲同帧配对保留。普通视频、带识别的完整输出和浏览器绘制分别计数。

## 为什么原先最高约 30 fps

原代码同时使用 `camera.Camera(..., fps=30)` 和每轮 `1/30` 秒调度。仅把数字改为 60，RGB 采集后再进入硬件 JPEG 的格式转换仍然消耗时间，完整视频约 36–38 fps。JPEG 已是硬件编码，换线程或再次封装编码器没有消除这项开销。

最终方案只创建 **一个摄像头通道**：普通模式沿用 NV21 到硬件 JPEG，避免 RGB 往返转换；本机需要预览时才将 NV21 转为 RGB。识别模式保持原来的 RGB 相机输入，不经过新转换器。切入/离开普通模式或 YOLO 时完整重启取图进程；YOLO 仍先加载模型再打开相机，所有相机、NN、JPEG 与显示调用仍由主线程持有。

电脑持续接收新帧时去掉额外的接收节流。标定状态使用 ETag 条件请求，内容未变时返回 304，避免每半秒在设备上重复深拷贝并序列化整份网格。标定、目标、接收地址/确认消息、成像兼容性或读取错误变化都会使标签失效，正常返回完整状态。

## 最终实测

具体数值、采样时长、源文件/产物哈希见以下 JSON，当前结果汇总见 [VALIDATION.md](VALIDATION.md)。所有视频测试使用 USB 网络，未测手机热点吞吐。

| 最终测试场景 | 普通模式 | YOLO11 |
|---|---:|---:|
| 热机后单客户端，连续 JPEG 接收/解码，每模式 120 秒 | 44.95 fps | 23.71 fps |
| 带标定/网格，EXE + Edge 实际绘制，各约 5 秒 | 44.76 fps | 22.39 fps |
| 两路设备订阅，上位机与独立测速同时运行，每模式 120 秒 | 40.53 fps | 21.08 fps |

单客户端长测的帧间隔 95% / 99% 分位数为普通 39.08 / 44.55 ms、YOLO 49.13 / 50.34 ms；平均接近设定帧率不代表每两帧恰好等间隔。首次接入可能有一次界面切换停顿，完整间隔统计见 JSON。

| 报告 | 计数含义 |
|---|---|
| `performance-baseline30.json` | 本轮恢复原 2.1.1 设备源码后的同场景基线，每模式约 20 秒 |
| `performance-unlocked60.json` | 单通道最终像素路径请求上限 60 的普通视频短测；在状态同步优化之前采样 |
| `performance-pc.json` | 最终源码的连续 JPEG 接收并实际解码，只计不同会话/序号 |
| `performance-dual-viewer.json` | 热机后同时运行上位机和独立测速客户端，两路设备订阅；普通约 40.5、YOLO 约 21.1 fps，每模式 120 秒 |
| `performance-calibrated-pc.json` | 本机合成标定并保存目标后的连续接收，每模式约 15 秒 |
| `pc-workflow-validation.json` | 最终 EXE + Edge + 真实相机，带标定网格时实际解码并绘制，每模式约 5 秒 |
| `pc-workflow-before-status-cache.json` | 条件状态同步之前的本轮浏览器回归，用于观察该额外开销 |
| `performance-standalone.json` | 无电脑订阅时的处理与本机屏幕重绘分别计数，每模式约 30 秒；状态同步优化前采样 |
| `stability-validation.json` | 最终 EXE 的连续 YOLO 观察；每秒抽样 JPEG 不作为视频帧率 |

基线、部分候选与最终复测来自不同采样窗口，期间重新上电且场景/照明有所变化。各报告保留所测源码与产物身份；不把这些窗口间的全部差值都归因于某一项优化。

热机后的正常单客户端复测，普通视频连续解码为 44.95 fps（120 秒）。同时让上位机和独立测速客户端各占一路相机流时，普通视频降至约 40.5 fps；这是额外订阅负载，不能与单客户端结果混用。慢客户端仍只取最新帧，多个查看端不会分别启动摄像头。

把上限填为 60 并不能得到 60 fps：最终单通道路径的普通视频短测只有约 46.5 fps。因此交付设为 45，连续实测速率随场景、光照、温度和客户端负载波动；没有把峰值当成持续能力。保留原识别负载时，YOLO 完整输出仍在二十多帧，不会因普通画面提速自动变成 45 fps。独立运行还需重绘本机 UI，实际屏幕刷新明显低于处理帧率。

探索过的双摄像头通道方案曾达到约 48 fps，但在完整标定/推理/重启回归中触发驱动等待，已弃用。Python 异步 JPEG、额外 C 编码器封装和把 NV21 转 RGB 再用于推理也没有足够收益，未作为交付依赖。交付的 3 KB `_pixel_ops.so` 只做内存像素转换，不申请摄像头或编码通道；其源码与重建工具随仓库提供。

## 为什么不能直接沿用旧标定

GC4653 在 30 与 60 fps 使用不同传感器时序。固定场景比对发现约 2.9 / 3.9 像素的平移；如果直接复用旧单应矩阵，地面坐标会产生系统偏差。参见官方 [MaixPy 4.10.3 相机文档](https://github.com/sipeed/MaixPy/blob/v4.10.3/docs/doc/zh/vision/camera.md) 对高速模式画面偏移的说明。

升级读取设备原有正式标定：若成像身份为旧的 `640x480-rgb-v1`，自动保留 30 fps 传感器与处理上限，不修改原标定或目标。无旧标定的设备采用 60 fps / 45 fps，以及新的 `640x480-sensor60-v2` 身份。身份不匹配时拒绝导入/使用标定；普通模式和三种识别模式在同一传感器时序下共用一套身份。

高速传感器模式还会缩短每帧可用曝光时间，低光照下的噪声和识别效果仍需按实际照明检查。本版没有主动降低识别分辨率、JPEG 质量或检测阈值来换帧率，也未做超频；已有正式旧标定继续保留原成像模式。

成像路径实机对齐结果见 `capture-geometry-validation.json`：普通 NV21 与识别 RGB 的静态特征匹配中位位移约 0.22 像素，95% 约 0.97 像素。像素转换用已知颜色及独立 OpenCV 参考验证，最大每通道差 1，见 `pixel-conversion-validation.json`。这两项不代表实际场地米制精度已经验收。

高级设置在设备 `/root/aic_vision/agent_config.json`：`performance_version:2`、`camera_fps:60`、`fps:45`。已有旧标定需要切换时，应先导出备份，完整停止应用后修改时序并重启，再按正式安装位置重新标定；新标定会按原功能清除旧坐标系目标。需要恢复旧成像时使用 `camera_fps:30,fps:30`。运行中修改文件不会即时生效。不要将私有令牌放入公开仓库。

## 复测

```powershell
python tools/check_performance.py --seconds 120 --output docs/performance-pc.json
python tools/check_performance.py --standalone --seconds 30 --output docs/performance-standalone.json
python tools/check_native.py --performance
python tools/check_pc_workflow.py
python tools/check_controls.py
python tools/check_yolo_regression.py
```

独立运行测速时断开其他电脑取图连接。流程工具只在无正式标定/目标的设备上创建合成数据，并清理自己的数据；已有正式数据时拒绝覆盖。保持相机和场景静止后可运行 `check_capture_geometry.py`；`check_pixel_ops.py` 使用合成像素，不改变识别输入。

`agent_frame_age_ms` 只在设备单调时钟上计量，从该帧读取返回到发送响应；不是曝光到电脑显示的延迟。不能直接相减设备时间与电脑时间。
