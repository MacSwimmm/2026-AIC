## 1.0.2 YOLO 重连故障

用户报告开启 YOLO 后重连报「旧取图程序处于内核等待状态」。现场上位机已离线，但直连设备 HTTP 状态显示 YOLO 帧序号从 2699 增至 2712；同一进程采样能看到 `R`、`S`、`D` 等状态。故障判断错误在于把一次 `D` 采样当作进程永久卡死。相机驱动 I/O 的正常等待也会进入该状态。

另一个问题是旧部署顺序在停止旧进程前写入新配置并更换令牌。若随后交接失败，仍在运行的旧进程保留旧令牌，上位机已经使用新令牌，导致取图进一步失败；配置里的模式也提前被重置。

1.0.2 移除对单次 `D` 状态的拒绝，改为发送正常退出信号并等待，必要时有界终止，确认进程退出后才启动新取图。待部署程序先写入独立临时文件，旧程序和配置在交接成功后才替换。超时不替换原连接凭据或配置。下面的实机记录按各 JSON 的版本与 EXE SHA-256 判定，旧版短时结果不能替代本版 YOLO 检查。

最终 1.0.2 打包版通过 `python tools/check_yolo_regression.py`，见 [yolo-regression-validation.json](yolo-regression-validation.json)：

- 十轮 YOLO → 关闭识别，每次均解码真实 JPEG 并确认新帧前进。开启耗时约 4.5～6.1 秒，关闭约 4.1～4.4 秒；包含等待新帧及解码检查的时间。
- 三次 YOLO 推理中重新连接，均成功恢复普通画面，约 9.4～9.6 秒；另一次断开后立即重连成功。
- 同一正常运行的 YOLO 进程连续采样 200 次：`R` 87 次、`D` 33 次、`S` 80 次，同时帧序号增加。这直接验证瞬时 `D` 不能作为卡死依据。
- 保持 YOLO 连续运行 **600.11 秒**：2,996 次状态读取、600 张真实 JPEG 解码、断线样本 0、错误 0。最大状态响应时间 0.0291 秒，最大新帧接收年龄 0.1681 秒。详情见 [stability-validation.json](stability-validation.json)。
- 检查结束恢复关闭识别，标定未修改。报告与最终 EXE 的 SHA-256 一致；该结果覆盖本次观察窗口。

随后通过真实浏览器按钮再次完成三轮连接，约 8.8～10.8 秒恢复并确认新帧；两次断开均只恢复一个原厂管理器与一个启动应用。页面冻结/解冻、红色模式 → YOLO11 → 关闭识别均成功，浏览器异常为 0，标定未修改。详见 [live-browser-validation.json](live-browser-validation.json)。

最终再检查普通取图、YOLO11、红色标记、AprilTag 四种模式，均返回 640×480 可解码新帧，报告约 11.8～11.9 fps。本轮 YOLO 采样检出人物，红色模式检出色块，AprilTag 无标签；未进行识别精度或实际标签距离验收。检查结束恢复关闭识别，详见 [live-validation.json](live-validation.json)。

## 1.0.1 连接问题复核

用户后续使用时出现持续等待和画面中断。故障现场，USB 网卡与 SSH 均可用，相机端帧序号仍前进；同一次对照请求，两个 USB IP 的设备状态响应均约 0.05 秒，设备 `.local` 名称约 4.18 秒。电脑端此时保留该名称作为每帧请求地址，导致旧画面超出有效期。直接切换 USB 地址后恢复连续取图。另复现了 SSH 名称连接长时间停留在等待阶段。

修复为名称解析单独限时、优先 USB 地址、认证后固定 SSH 实际对端 IP、传输中断自动恢复，以及设备 I/O 不持有地面标定锁。连续运行工具记录状态采样、断线样本、真实 JPEG 解码和最大响应时间，不记录现场照片或相机身份。

1.0.1 曾在关闭识别后连续观察 **180.08 秒**：899 次状态读取、180 张真实 JPEG 成功解码、断线样本 0、错误 0；状态接口最大响应时间 0.0269 秒，最新帧的最大接收年龄 0.1283 秒。该记录保存在 Git 历史提交 `1efec12`，只覆盖普通取图，不能作为长时间 YOLO 运行证据。

复核还发现设备原启动应用为设置程序，旧版连接只停止 `launcher`，可能留下设置程序继续持有图像资源；旧版取图退出时也会在解释器释放本地资源前恢复界面。现场曾出现多个设置进程、图像分配失败与内核等待。1.0.1 改为等待资源所有者完整退出再交接，原厂界面恢复也延后到取图进程退出。该观察支持修正交接顺序，不能据此把所有 USB 故障都归因于同一处。

另曾观察到 Windows「未知 USB 设备（设备描述符请求失败）」及两个网络接口一起消失。当时电脑连设备身份都读不到，属于低于画面传输层的故障；数据线、接口、供电或设备侧 USB 状态需要单独排查。该现象本身不能证明硬件损坏。

## 实机运行与现场边界

设备为 MaixCAM Pro，MaixPy 4.10.3。原本相机初始化及模型加载发生本地库崩溃；调用设备自带的 Sipeed 安装程序重新安装官方 1.22.0 运行库后，取图恢复。修复后曾成功执行 YOLO11 推理。

连续切换检查发现，同一进程中先打开相机再加载 YOLO 时设备失联；仅关闭相机后加载仍有异常。独立进程中按官方例程先加载模型、再打开相机，连续 10 帧识别到人物。最终实现进入/退出 YOLO 时重启取图进程；修复后真实设备依次执行普通取图、红色标记、AprilTag、YOLO11，并返回普通取图成功。该结果验证了调整的效果，不能据此断言底层库失效的具体机制。

最终连续模式检查由 `python tools/check_live.py` 记录。该工具检查真实 JPEG 解码、图像尺寸、帧序号前进和模式切换；发生失败时也保留部分结果，不会把已通过的基础取图替代未通过的模式检查。可用 `--modes off red_blob apriltag` 进行指定模式检查。实机结果以本目录的 `live-validation.json` 为准。

目前没有在实际安装位置量出 5 × 5 米区域并完成四点标定，也没有测量现场定位误差。没有使用真实 AprilTag 标签做识别距离或定位精度验收。红色阈值需要在实际光照下检查，YOLO 框底中心只是接地点近似。

使用者需固定相机，实测矩形尺寸，按 A → B → C → D 选地面角点，并在近处、远处、四周和中间另外量点检查误差。物品顶部与被遮挡地面不能直接按可见地面换算。
