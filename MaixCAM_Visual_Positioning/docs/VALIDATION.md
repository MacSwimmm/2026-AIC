## 1.0.1 连接问题复核

用户后续使用时出现持续等待和画面中断。故障现场，USB 网卡与 SSH 均可用，相机端帧序号仍前进；同一次对照请求，两个 USB IP 的设备状态响应均约 0.05 秒，设备 `.local` 名称约 4.18 秒。电脑端此时保留该名称作为每帧请求地址，导致旧画面超出有效期。直接切换 USB 地址后恢复连续取图。另复现了 SSH 名称连接长时间停留在等待阶段。

修复为名称解析单独限时、优先 USB 地址、认证后固定 SSH 实际对端 IP、传输中断自动恢复，以及设备 I/O 不持有地面标定锁。连续运行检查见 [stability-validation.json](stability-validation.json)：记录状态采样、断线样本、真实 JPEG 解码和最大响应时间，不记录现场照片或相机身份。该检查的结论仅覆盖报告中实际观察的时间窗口。

最终打包版在四种模式检查结束并恢复关闭识别后，连续观察 **180.08 秒**：899 次状态读取、180 张真实 JPEG 成功解码、断线样本 0、错误 0；状态接口最大响应时间 0.0269 秒，最新帧的最大接收年龄 0.1283 秒。标定与识别模式未改变。三份实机报告均记录与发布包一致的 EXE SHA-256。该短时结果不能排除间歇性的线材、接口或供电故障。

复核还发现设备原启动应用为设置程序，旧版连接只停止 `launcher`，可能留下设置程序继续持有图像资源；旧版取图退出时也会在解释器释放本地资源前恢复界面。现场曾出现多个设置进程、图像分配失败与内核等待。1.0.1 改为等待资源所有者完整退出再交接，原厂界面恢复也延后到取图进程退出。该观察支持修正交接顺序，不能据此把所有 USB 故障都归因于同一处。

另曾观察到 Windows「未知 USB 设备（设备描述符请求失败）」及两个网络接口一起消失。当时电脑连设备身份都读不到，属于低于画面传输层的故障；数据线、接口、供电或设备侧 USB 状态需要单独排查。该现象本身不能证明硬件损坏。

## 实机运行与现场边界

设备为 MaixCAM Pro，MaixPy 4.10.3。原本相机初始化及模型加载发生本地库崩溃；调用设备自带的 Sipeed 安装程序重新安装官方 1.22.0 运行库后，取图恢复。修复后曾成功执行 YOLO11 推理。

连续切换检查发现，同一进程中先打开相机再加载 YOLO 时设备失联；仅关闭相机后加载仍有异常。独立进程中按官方例程先加载模型、再打开相机，连续 10 帧识别到人物。最终实现进入/退出 YOLO 时重启取图进程；修复后真实设备依次执行普通取图、红色标记、AprilTag、YOLO11，并返回普通取图成功。该结果验证了调整的效果，不能据此断言底层库失效的具体机制。

最终连续模式检查由 `python tools/check_live.py` 记录。该工具检查真实 JPEG 解码、图像尺寸、帧序号前进和模式切换；发生失败时也保留部分结果，不会把已通过的基础取图替代未通过的模式检查。可用 `--modes off red_blob apriltag` 进行指定模式检查。实机结果以本目录的 `live-validation.json` 为准。

目前没有在实际安装位置量出 5 × 5 米区域并完成四点标定，也没有测量现场定位误差。没有使用真实 AprilTag 标签做识别距离或定位精度验收。红色阈值需要在实际光照下检查，YOLO 框底中心只是接地点近似。

使用者需固定相机，实测矩形尺寸，按 A → B → C → D 选地面角点，并在近处、远处、四周和中间另外量点检查误差。物品顶部与被遮挡地面不能直接按可见地面换算。
