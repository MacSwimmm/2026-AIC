# 2.0.0 验证记录

本次修改：独立 MaixCAM 菜单应用、本机屏幕/触屏操作、本机地面换算与持久化、电脑编辑同一份设备数据，以及目标点发送/接收接口。软件功能、真实设备运行、现场定位精度和真实树莓派执行分别记录。

## 软件检查

`python -m unittest discover -s tests -v`：**50 项通过**。保留原有几何、镜头、输入边界、HTTP 来源、帧有效期及进程退出测试，并增加：

- 设备标定/目标点在同一原子文件保存；重开存储读取同一修订号与坐标。
- 模拟写入失败时不确认成功、不改变内存中的已保存数据。
- 新标定同时清除旧坐标系目标点；过期帧/错误相机不能添加目标。
- 不自动读取电脑旧测试文件；损坏的数据保留以便恢复。
- 触屏缩放坐标与设备端几何算法一致。
- 接收示例保存相同批次，发送方验证匹配请求 ID/修订号，拒绝旧回执。
- 恢复系统菜单时清除仅供 YOLO 内部 exec 使用的文件描述符环境，避免新菜单应用继承失效锁句柄。

`python tests/browser_check.py`：桌面 1440 × 1050（DPR 2）、移动窗口 390 × 844 通过，脚本异常 0。覆盖四点标定、点击坐标、目标保存、独立校验点、区域外点、冻结、恢复连接中保留未完成角点与断线禁用操作。使用独立模拟设备存储及合成画面；截图不是现场误差证明。结果见 `browser-validation.json`。

## MaixCAM 本机屏幕与持久化

`python tools/check_native.py` 使用真实 MaixCAM Pro 的相机、显示屏、MaixPy 和 Linux 输入设备，在空白标定状态注入触摸事件：

- 屏幕数字键盘输入 1 × 1 米测试尺寸，冻结预览，依次选 A/B/C/D 并保存。
- 点击预览中的已知合成坐标位置，在本机保存目标点。
- 回读设备 `/root/aic_vision/data/ground.json`，与设备 API 导出坐标逐项一致。
- 完整停止/重启已安装应用后，原标定、目标点、坐标及修订号一致。
- 点击屏幕「退出应用」，确认仅恢复一份原厂管理器与原启动应用。
- 通过实际系统管理器启动已注册的 `aic_ground` 菜单入口，恢复同一批数据。
- 检查结束清除验证所创建的临时标定和目标点，保留电脑原临时资料。

见 `native-validation.json`，其中包含对应原生安装包 SHA-256。真实相机画面与屏幕绘制图像仅保留在本地 `data/qa/`，不提交公开仓库。

这里验证了软件触摸事件路径和真实显示调用，**没有代替使用者的手指触摸体验、实际场地角点或实测定位误差验收**。保存执行文件及目录同步；本轮没有做反复拔电或存储卡故障耐久测试。

## MaixCAM 到接收示例的通信

`python tools/check_pi_delivery.py` 在真实 MaixCAM 应用上创建临时合成标定及目标，通过设备 `/api/pi/send` 发起 HTTP 请求，经过 USB 网络到电脑运行的同一份 `examples/pi_target_receiver.py`：

- 接收程序确实落盘相同目标点、相机/标定版本与修订号。
- 请求 ID、修订号匹配后，设备回复接收成功。
- 清除临时标定/目标，并恢复原接收 URL。

结果见 `pi-delivery-validation.json`。这是**真实设备发送到电脑接收示例**的通信检查；没有连接真实树莓派，也没有导航地图对齐或车辆运动。树莓派后续可直接运行同一接收示例，仍需验证实际网络和导航集成。

## Windows 打包与实机识别

`MaixVisionConsole.exe` 为更新后的 2.0.0 独立程序。`python tools/verify_package.py` 核对网页、设备源文件、几何文件及电脑编译代码与源码一致；文件大小和 SHA-256 在 `release-manifest.json`。

实机网页连接/断开、识别模式、新 JPEG 和连续 YOLO 的最新结果分别记录于：

| 文件 | 范围 |
|---|---|
| `live-browser-validation.json` | 打包 EXE 的网页连接/断开，确认断开电脑后本机应用继续运行，冻结/解冻及识别切换 |
| `live-validation.json` | 普通、YOLO11、红色标记、AprilTag 的真实 JPEG 解码、分辨率、帧序号与采样识别结果 |
| `yolo-regression-validation.json` | 十轮 YOLO 开关、推理中重连、立即重连及连续运行 |
| `stability-validation.json` | 指定模式连续取图窗口、断线样本、JPEG 解码和响应时间 |

**每份 JSON 的 `application_version` 和 EXE SHA-256 必须与本次产物对应**；旧版结果不作为新版验收。屏幕绘制和本机处理增加了工作量，帧率以本版实机报告为准，不沿用 1.0.2 的 11.8～11.9 fps。

本版四模式实机采样均为 640 × 480 JPEG，帧序号持续前进；普通画面、YOLO11、红色标记、AprilTag 的采样报告分别为 9.4、7.2、7.9、6.8 fps。这是短时运行采样，不是帧率保证。本轮采样没有检出目标，证明的是取图和推理流程运行，目标识别准确率仍需用现场实物验收。

首次连续 YOLO 观察期间，使用者手动切换了识别模式（已由使用者确认），记录到 15 个离线采样及最终模式改变，因此该轮不作为连续 YOLO 通过依据。原始观察保留在回归报告的 `interrupted_observation`，连续运行结果使用重新开始、保持 YOLO 模式的独立观察。

最终检查通过十轮 YOLO 开关、三次推理中重连及立即断开重连；重连保持 YOLO 模式。补测连续 YOLO 600.18 秒，2,996 次状态采样、600 张 JPEG 解码，离线采样 0、解码/请求错误 0，最大采样帧龄 0.283 秒。结束后恢复普通画面，标定未改变。该帧龄为电脑接收有效期指标，不是相机到屏幕的端到端延迟。

## 保留的历史修复依据

1.0.2 基线提交为 `d003212e3c90d4bc74a3a8b2e4d018b7c3a8910e`，完整历史报告可从该提交读取。此前设备相机/模型初始化曾在本地库中崩溃，经原厂安装程序重装官方 1.22.0 运行库恢复；不是本版正常使用步骤。

同一进程中相机先初始化、随后再加载 YOLO 曾导致失联，因此仍在进入/退出 YOLO 时完整重启取图进程，并先加载模型再打开相机。普通标记模式之间无需重启。Linux 单次 `D` 状态只是驱动等待，仍采用有界退出等待判定；失败交接不改旧配置/凭据。相机和 NN/显示缓冲只由主线程操作。

连接优先 USB 数字地址，名称解析单独限时并固定已认证的实际对端 IP，传输中断不反复部署。USB「设备描述符请求失败」属于独立的底层连接问题，应用重试不能替代数据线/接口/供电检查。
